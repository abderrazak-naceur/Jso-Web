# Team/Roster and Sponsors screens behind a new Club tab (v1)

Adds two public areas to the JSO Flutter app: a Teams list that drills into a per-team roster, and a Sponsors list with external website links. Both follow the established `StatefulWidget` + `FutureBuilder` pattern with `LoadingView`/`ErrorView`/`EmptyView`, Provider-supplied `PublicApiRepository`, JSO theme tokens, and `RemoteImage`. Rather than crowd the fixed `BottomNavigationBar` with two more tabs, the work adds a single fifth "Club" tab hosting a landing screen that pushes to Teams and Sponsors — a sensible call that's documented in the README. `url_launcher` is the one new dependency, used only on the Sponsors screen.

Watch for: the sponsor link handler only treats a `false` return from `launchUrl` as failure and does not catch the `PlatformException` that `launchUrl` can throw instead (confirmed); the branch also carries an unrelated LiveBlog backend/frontend commit that has nothing to do with this feature (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The screens are faithful to the existing patterns — same state-handling skeleton as `media_screen.dart`/`match_detail_screen.dart`, same theme tokens, same `RemoteImage` fallback behavior — and the roster's circular-avatar treatment and sponsor logo box are reasonable extensions rather than new inventions. There is nothing surprising in the topology: the Club tab is a pure navigation shell.

The sponsor link path is the one behavioral gap. `launchUrl` is documented to either return `false` or throw a `PlatformException` depending on the failure, and the handler only covers the `false` branch, so a throwing failure escapes uncaught and the user never sees the "Could not open link." SnackBar. The guard against null/empty/unparseable URLs is otherwise solid.

Test coverage is genuinely meaningful — LOADING/EMPTY/ERROR/populated for all three screens plus a real tap-through from Teams into the roster — and asserts screen-specific content rather than trivia. The gaps are the untested sponsor-link tap and the stale "four tabs" assertion in the pre-existing `widget_test.dart`.

The diff bundles an unrelated LiveBlog change (backend controllers, a migration, and a frontend admin screen) that belongs to a different feature and should not ride along in this branch.

### Sponsor link failure handling

`_openWebsite` treats null/empty/unparseable URLs as `opened == false` and raises the SnackBar behind a `mounted` check. The gap is the `launchUrl` call itself:

```dart
if (uri != null) {
  opened = await launchUrl(uri, mode: LaunchMode.externalApplication);
}
if (!opened && mounted) {
  ScaffoldMessenger.of(context)
      .showSnackBar(const SnackBar(content: Text('Could not open link.')));
}
```

url_launcher documents `launchUrl` as: "Returns true if the URL was launched successfully, otherwise either returns false or throws a `PlatformException` depending on the failure." (confirmed, `url_launcher_uri.dart` line 37–38). The handler only covers the `false` branch. When the platform throws instead — for example a URI that parses but has a scheme no installed app handles — the exception propagates out of the async callback uncaught and the user never sees the failure SnackBar. Wrapping the `launchUrl` call in try/catch and routing the catch into the same `!opened` SnackBar path closes this, and keeps the failure fail-safe (user-visible) rather than silent.

### Test coverage

Every new screen has LOADING (via `FakeRepository` delay), populated (asserting real content — team names and categories, `Ali Ben Salah` / `Milieu` / `#10`, sponsor name + tier + "Visit website"), EMPTY (`const []`), and ERROR-with-Retry (`ApiTimeoutException`) coverage. The Teams suite additionally taps a tile and asserts it lands on `TeamRosterScreen` with a player rendered, so navigation is exercised end to end, and the Sponsors suite verifies the "Visit website" affordance is hidden when `websiteUrl` is null. These fail if the screens are reverted, so they're real.

Not tested: the sponsor-link tap path — the tests assert the affordance exists but never trigger `_openWebsite`, so the failure-SnackBar behavior (and the uncaught-exception gap above) has no coverage. A test that pumps a sponsor with an unlaunchable URL, taps "Visit website", and expects the SnackBar would both document intended behavior and catch the exception hole. Separately, the pre-existing `widget_test.dart` still asserts "four tabs" and only checks the four original labels; it passes but no longer describes the shell, and nothing asserts the Club tab is present.

### Unrelated LiveBlog change bundled in the branch

`git log feat/flutter-mobile-app..feat/flutter-team-sponsor-screens` shows commit `ef17f55 feat(liveblog): match day live blog / second screen` sitting between the `url_launcher` chore and the mobile feature commit. It adds `AdminLiveBlogController.cs`, `LiveBlogController.cs`, `LiveBlogEntry.cs`, an EF migration, and `frontend/src/admin/LiveBlog.jsx` — roughly 1,200 lines with no connection to the Flutter team/sponsor scope. Reviewing and shipping it under this branch mixes two features and obscures the actual change; it should be moved to its own branch so this diff is limited to `mobile/`.
