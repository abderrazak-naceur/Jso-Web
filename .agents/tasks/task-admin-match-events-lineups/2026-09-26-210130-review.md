# Admin match event editing + lineup formation editors (v1)

Adds edit support to the admin match-events editor and introduces a new formations (lineup) editor. On the backend the `MatchEvent` entity gains two nullable columns (`SecondaryPlayerName`, `Team`), a new `PUT /events/{eventId}` endpoint mirrors the create-path validation, `AddEvent` now persists the two new fields, and a non-unique index is added on `MatchEvents.MatchId`, backed by a versioned Postgres migration and an updated model snapshot. On the frontend the `EventsModule` gains an inline edit flow plus the two new fields, and a new `FormationsModule` builds a match lineup (starters/bench, position, order, single captain) against the pre-existing lineup endpoints. Public read contracts were left unchanged and remain backward compatible.

Watch for: the `Team` value coming back from the public/admin GET is the entity as-is, so any consumer that assumed a fixed shape now sees two extra nullable fields (confirmed, additive only — not breaking). The new formations editor relies entirely on the pre-existing `ReplaceLineup` endpoint for persistence, which does **not** enforce single-captain server-side — the single-captain guarantee is client-only (confirmed).

**Verdict**: APPROVED

## High-level view

The event editing path is a clean mirror of the create path: `UpdateEvent` scopes the lookup by both `eventId` and `matchId`, runs the same minute/type/team validation, and writes an `UPDATE`/`MatchEvent` audit record keyed on the event id. Validation parity with `AddEvent` is exact, including the shared `TryNormalizeTeam` helper that treats empty/whitespace as a legitimate null and rejects anything other than Home/Away case-insensitively.

The schema change is additive and internally consistent: entity, DbContext index, migration Up/Down, and snapshot all agree on two nullable `text` columns plus a non-unique `IX_MatchEvents_MatchId`. Public read endpoints return the entity directly, so the new fields surface automatically without a contract break.

The formations editor is new UI over an unchanged backend. It wires to `GET/PUT /admin/matches/{id}/lineup` and `GET /admin/teams/{teamId}/players`, builds the exact `{ items: [{ playerId, role, positionOrder, position, isCaptain }] }` payload the endpoint expects, and enforces one captain in the browser. Because `ReplaceLineup` does not validate captain uniqueness, that invariant is only as strong as the client.

<summary>Details</summary>

### UpdateEvent scoping and validation parity

`UpdateEvent` loads the row with `SingleOrDefaultAsync(x => x.Id == eventId && x.MatchId == id)`, so an event id from one match cannot be edited through another match's route — a mismatched pair returns 404 rather than silently editing the wrong row or leaking existence. The three validation gates (minute 0..200, non-empty type, normalized team) are byte-for-byte identical to `AddEvent`, and both share `TryNormalizeTeam`, so the create and update paths cannot drift apart in what they accept. The audit call logs `UPDATE`/`MatchEvent` with the event id as the entity key and `{ matchId }` as detail, symmetric with the `CREATE` record on the add path.

`TryNormalizeTeam` treats empty/whitespace as a valid null and forces stored values into fixed `"Home"`/`"Away"` casing (case-insensitive on input), which is what the frontend `EVENT_TEAM_LABELS` lookup and the `Home`/`Away` option values depend on.

### Schema change consistency

Entity, DbContext, migration, and snapshot agree: two nullable `text` columns and a non-unique `IX_MatchEvents_MatchId` (correct, since a match has many events), with a `Down` that drops the index and both columns. Migration timestamp `20260926150000` orders after existing migrations, and no backfill is needed — existing rows get NULL for both new columns.

### Public read backward compatibility

`MatchDetailsController.GetEvents` and the admin `GetEvents` return the `MatchEvent` entity directly, so the two new nullable fields surface as `null` for old rows. Additive: no read endpoint changed, and the public lineup read (`PublicMatchDetailsController`) is untouched. The one thing to be aware of is that any consumer strictly validating the event shape now sees two extra fields.

### Frontend event edit flow

`EventsModule` carries an `editingId` and a shared `save` handler that branches to `PUT .../events/{editingId}` or `POST .../events` off the same form state. Empty `secondaryPlayerName`/`team` are coerced to `null` before send, so clearing a field clears it server-side rather than storing an empty string. Switching the selected match resets `editingId` and the form, and deleting the row currently being edited cancels the edit — the form can't end up bound to a stale or deleted event.

### Formations editor wiring and captain handling

`FormationsModule` merges the roster from `GET /admin/teams/{teamId}/players` and the lineup from `GET /admin/matches/{id}/lineup` into a per-player `rows` map. On save it emits exactly `{ items: [{ playerId, role, positionOrder, position, isCaptain }] }`, with `positionOrder` as `null` when blank (`Number(...)` otherwise) and `position` as `null` when empty — the shape `ReplaceLineup` deserializes into `LineupItem`. `role` is constrained to `Starter`/`Substitute` by the select, matching the endpoint's role check.

`setCaptain` rebuilds the rows map with `isCaptain` true only for the chosen player, enforcing a single captain in the UI. The backing `ReplaceLineup` endpoint (pre-existing, unchanged) validates team membership and role but does not check captain uniqueness — so the single-captain rule holds only as long as this UI is the sole writer. Flagged in Issues.

The empty-roster branch reuses a lineup-flavored message ("Aucune formation enregistrée."), which misleads when the real cause is an empty team roster rather than a missing lineup. Flagged in Issues.
