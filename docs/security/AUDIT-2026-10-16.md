# JSO-Web Security Review — 2026-10-16

## Scope and limitations

This is a source-code review of selected authentication, public content, configuration, and CI files. It is not a full penetration test, and no production database contents or private Render environment variables were inspected. Findings below distinguish confirmed code behavior from areas that still need dedicated testing.

## Confirmed finding

### SEC-001 — Public content API returns internal configuration keys

- **Severity:** Medium (potential information disclosure; actual impact depends on stored values)
- **Location:** `backend/src/JSO.Api/Controllers/ContentController.cs`
- **Evidence:** The unauthenticated `GET /api/content` endpoint previously excluded only `i18n:` keys and serialized every other `SiteContents` entry. The authenticated admin content API explicitly excludes `__system.` keys and `DonationCampaignSettings.ContentKey`, indicating these entries are not intended for the generic content endpoint.
- **Impact:** Any values stored under internal/system keys or the dedicated donation-campaign key could be read by an unauthenticated caller. The review did not establish that secrets are currently stored there.
- **Fix on this branch:** Filter `__system.`, `i18n:`, and `DonationCampaignSettings.ContentKey` at the database query before serializing the public response.
- **Validation needed:** Run backend build/unit tests and verify that public content still contains the keys required by the frontend while excluding the three internal categories.

## Areas reviewed; no specific exploitable issue confirmed from the inspected snippets

- **Admin login:** The inspected endpoint requires non-empty credentials, verifies the password hash, checks active users, and applies an `auth-login` limiter of 5 requests per 5 minutes. A broader review of password reset, account creation, and privilege changes is still needed.
- **JWT validation:** The inspected startup configuration validates issuer, audience, lifetime, and signing key, and checks whether fan accounts remain active. The actual production key and all role/permission policies were not audited.
- **CORS:** The API uses a fixed origin allowlist; no wildcard origin was seen in the inspected configuration.
- **Payment return URLs:** The inspected URL builder refuses to derive production return URLs from the request Host header when no configured public URL is available.
- **Swagger:** Swagger UI is enabled only in Development in the inspected startup file.
- **CI:** The inspected workflow builds the frontend/backend and runs route/backend tests. This review did not run those jobs itself or complete a dependency/SAST scan.

## Recommended next checks

1. Run the repository's GitHub Actions on this branch and fix any failures.
2. Review all public endpoints that serialize database entities or settings, especially fan accounts, orders, tickets, payment callbacks, and uploads.
3. Verify production environment variables and rotate any real credentials accidentally committed to Git history; do not paste secrets into issues or chat.
4. Add a regression test for `GET /api/content` proving internal keys are omitted.
5. Run dependency and static-analysis scans, then do authenticated/unauthenticated role-based endpoint testing before deployment.
